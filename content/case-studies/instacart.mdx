## Problem

I wanted a SQL project at a real size, where schema design and index choices matter and a live dashboard runs real queries. There was no client or stakeholder. My goal was to show SQL skills from end to end, not on a toy dataset.

## Architecture

- The Instacart Market Basket CSV files from Kaggle are loaded into PostgreSQL by a Python script, in chunks of 100,000 rows.
- Five tables with primary keys, foreign keys and NOT NULL constraints: `orders`, `order_products`, `products`, `aisles` and `departments`.
- Seven SQL files, from basic to advanced: joins, CTEs, window functions, RFM and cohort analysis, views, indexing, and stored functions with a trigger.
- Three views and two materialized views, `mv_department_stats` and `mv_top_products`.
- A Streamlit dashboard with five pages reads a Neon cloud Postgres database. Query results are cached for 10 minutes.

## Key decisions

1. **Materialized views for the dashboard.** The Overview and Product pages read `mv_department_stats` and `mv_top_products`. They do not aggregate the 33.8M `order_products` rows on every page view. The cost is that the views need a manual `REFRESH`.
2. **Seven indexes, including a composite and a partial one.** The partial index covers only `reordered = 1`. I wrote the reason in the file: it speeds up reorder analysis without indexing every row. The cost is index size, which the file also queries.
3. **Proxies where the data has no money.** The dataset has no prices. So "Monetary" in the RFM query and the customer lifetime value tiers use item counts, with thresholds of 100, 200 and 500 items. "Recency" uses the highest order number, not days. These are weaker signals than real recency and spend, and my SQL comments say so.

## Data quality and evaluation

- Schema constraints: primary keys, foreign keys, NOT NULL, and a composite primary key on `order_products`. The loader fills the tables in foreign-key order.
- An audit trigger on `products` logs every update and delete to `product_audit_log`.
- My performance file runs EXPLAIN ANALYZE on three queries before and after the indexes. I did not save the output, so I have no speed-up to report.
- There are no tests and no row-count check after loading.

## What I'd do next

My limits: no saved timings, no tests, and no row-count check after loading.

Next, I'd script the load into Neon instead of doing it by hand. I would save the EXPLAIN ANALYZE output, so the index work has numbers. I would add row-count checks after loading. And I would replace the item-count proxies with real recency in days, since the data has `days_since_prior_order`.
